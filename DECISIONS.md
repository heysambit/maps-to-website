# Architectural decisions

These are working defaults for the first implementation. The product direction comes from the operator-first brief. Validate the provider-dependent defaults at their backlog gates and record revisions here with the date, evidence, and affected milestones.

| ID | Decision | Alternatives and consequences |
| --- | --- | --- |
| ADR-01 | One studio per installation, with named operators and multiple business projects. | Full multi-tenant SaaS would add tenant onboarding, billing, and isolation work. The initial boundary is simpler and still requires project-scoped data and explicit role checks. |
| ADR-02 | Use Places API (New) for attributed listing identification. Store the selected ID as metadata and collect independent publishing inputs. Feature-flag live lookup until reviewed. | Scraping and copying Places fields into generated sites conflict with the product's policy boundary. Manual intake is the supported fallback and makes local use independent of Google. |
| ADR-03 | One Astro renderer shared across live, frozen, static, and CMS views. Templates are deterministic. Optional AI proposes copy with source IDs. | Separate preview components would create drift. Generated Astro code would raise review, reproducibility, and injection risks. Template versions must be retained for revisions still eligible for release. |
| ADR-04 | Cloudflare Workers for the private builder and per-site Workers Static Assets for public sites. D1 and R2 remain private to the builder. | Pages could host static output. Using Workers for both runtime shapes keeps the deployment toolchain aligned and supports per-site release versions. Confirm account quotas before adding sites. |
| ADR-05 | Named review through Cloudflare Access plus a project/revision grant. Frozen review rounds expire after seven days by default. | A bearer-only link would be easier to forward. Named enrollment adds operator work and prevents possession of the URL from granting access. |
| ADR-06 | Record external payment and owner authority. Require exact-revision approval and explicit release. Use protected manual CI dispatch with single-writer deployment and reconciliation. | Automatic checkout and deployment increase the operational surface. Manual evidence supports the first paid pilots, with a durable and auditable gate. |
| ADR-07 | Treat EmDash as a post-purchase option. Seed it into isolated site resources and switch traffic only after acceptance. | CMS during preview adds onboarding and makes disposable drafts expensive. Static and CMS modes share rendering but have distinct lifecycles. Test seed and final-host identity with the pinned EmDash version. |
| ADR-08 | MIT for original repository code, docs, and starter templates. Respect upstream notices for dependencies and generated component code. | A copyleft license would place different obligations on redistributed commercial adaptations. MIT is the proposed permissive choice. Export business content under its separate rights and keep Google material outside the export. |

## Rights and release record

Maintain `THIRD_PARTY_NOTICES.md` when third-party assets or component code are added. Record license and origin for copied shadcn components, icons, fonts, media and runtime packages as applicable. Keep the MIT notice with redistributed project code and generated source exports that contain it. The operator confirms the right to use each business asset for the private demo and again for publication. Record attribution and allowed uses in the asset inventory. Customer data, marks, photography, Google materials, and secret-bearing configuration are outside the repository license.

At M0, confirm compatible runtime versions and the planned Cloudflare resources. At M2, record applicable Google terms and reviewed field masks, disclosures, and budget controls. At M4, record Access bypass tests and reviewer enrollment. At M5, validate target domain operations, account limits, credentials, and reconciliation. At M6, prove EmDash seed, permissions, cutover, migration recovery, and exit/export on staging before offering that feature. ## M6 EmDash handoff — 2026-11-07

- **Pinned starter and seed contract:** Started from the official EmDash Cloudflare starter at release `emdash@1.4.0`, commit `10beb8c5a99e41c3a8554b09ac5123c4dddc8d11`; exact runtime dependencies and transitive graph are pinned. The upstream Cloudflare MIT notice is preserved. The starter seed now declares an empty `landing_pages` model and includes no synthetic/customer content. The supported `emdash/seed` contract is `validateSeed(seed)` and `applySeed(db, seed, options)`; release seeding uses `includeContent: true`, `onConflict: "skip"`, and `skipMediaDownload: true`. EmDash documents conflict handling per seeded entity rather than as a transaction for the whole seed, so the app records a lease/failed/succeeded marker and retries partial failures without updating an existing content entry.
- **Isolation and serving path:** Each site receives its own Worker, D1, private R2, final host, owner email and Access audience. Admin middleware verifies the Cloudflare Access assertion's signature, issuer and audience and requires the exact owner email and configured final host. CMS/admin/bootstrap and cutover flags default off. The shared static release remains the serving path; the template's deploy command refuses deployment.
- **Local evidence and limits:** Stub tests cover entitlement rejection, repeat seed after owner edit, partial failure recovery, in-flight duplicate dispatch, bootstrap/identity/host failures, unsafe stored CMS destinations/assets, service-area address suppression, retention dry-run selection and preservation of live/rollback assets. The retention planner has no deletion capability. The official API docs match the exact package version and the template is locally typechecked. Cloudflare Access behavior, actual EmDash draft/publication permissions, site isolation on real D1/R2, final-host setup, real migration and recovery, owner invitation/export, and traffic cutover were not tested under live-provider authorization. Do not enable the CMS option until the staging gates in the template runbook are completed.

## M2 Places review — 2026-11-06

- **Terms and allowed use:** Reviewed the current [Google Maps Platform terms](https://cloud.google.com/maps-platform/terms) and [Places policies](https://developers.google.com/maps/documentation/places/web-service/policies). This implementation is limited to project-scoped identification; it does not use results to create leads, enrich prospect records, train or evaluate AI, or derive publishable facts. Applicable billing-region terms and the final commercial flow still need operator/legal review before a staging enablement.
- **Field mask and attribution:** The real adapter requests only `places.id,places.displayName,places.formattedAddress,places.attributions` for Text Search and `id,displayName,formattedAddress,attributions` for Place Details. No photos, reviews, ratings, geometry, opening hours, or business attributes are requested. The current field catalog places `displayName` in Pro, so these masks have the Pro SKU cost tier for Text Search and Place Details; the actual billing account and budget still need review. Results are rendered transiently in visually separate cards with Google's official attribution logo and provider attributions when returned. The official logo file is unmodified and noted in `THIRD_PARTY_NOTICES.md`; final account/region disclosures still need review before live use. API responses are not saved or exported.
- **Privacy:** Search text and provider results are not logged or persisted. Selection assertions contain only project, operator, eligible Place IDs, and five-minute expiry. D1 retains only the explicitly selected Place ID and actor/time/action/status audit metadata. Local and integration tests use synthetic sentinel values and fake results. Google's policy requires publicly available Terms of Use and Privacy Policy incorporating Google's terms and privacy policy; these public documents have not been added, so live lookup stays off until the applicable disclosures are published and reviewed.
- **Credentials and billing:** No Google key is present. The real adapter is selected only when `PLACES_LOOKUP_ENABLED=true`, `APP_ENV=staging`, and a server-side `GOOGLE_PLACES_API_KEY` is configured. Code bounds each search to five results, 3.5 seconds upstream/4 seconds at the route, eight lookup requests per operator per minute and 60 per installation per minute. Live use still requires a dedicated restricted Places API (New) key, approved server egress restriction, billing owner approval, account-specific budget/quota limits and monitoring, and an authorized staging verification. [Google key security guidance](https://developers.google.com/maps/api-security-best-practices) and [Places usage and billing](https://developers.google.com/maps/documentation/places/web-service/usage-and-billing) were reviewed. Do not enable until those prerequisites and applicable terms review are recorded.
- **Decision:** Keep real lookup disabled. Local development and automated tests use the fake provider; production fixture identities remain rejected by middleware.

## M4 private review implementation — 2026-11-07

- **Identity and host boundary:** Deployable requests require a Cloudflare Access JWT from `Cf-Access-Jwt-Assertion`, verified with RS256 against the configured Access team cert endpoint. The Worker checks issuer, exact role-specific audience, expiration, email syntax/normalization, and an operator email allowlist. It also requires the configured HTTPS operator or reviewer hostname; this makes a valid token for the intended application insufficient on a raw origin, `workers.dev`, or deployment-preview hostname. Cloudflare Access must still be configured with separate operator and reviewer applications/audiences and the approved host routing. Local identities remain limited to loopback development fixtures.
- **Frozen rounds and grants:** Each review round references a canonical `sealRevision` snapshot and stores its content hash. Named grants are bound to the review, project, and exact revision, use viewer/approver roles, and expire at seven days. Approval and request-changes decisions are immutable records. New rounds supersede previous rounds; explicit whole-review and per-grant revocation remove access, and revoking the approving grant invalidates the approved round. The `/r/<revision-id>` URL identifies content but grants no authority.
- **Protected output:** Review pages render through the shared Astro landing renderer with inert CTAs. HTML, reviewer assets, and mutation responses are private/no-store, noindex, and no-referrer. Review assets require a digest included in the frozen revision, matching project metadata, cleared rights metadata, and an authorized current grant. Mutations require a same-origin `Origin` in deployable environments.
- **Evidence and limits:** Local D1/R2 tests exercise signed-out, wrong email/audience/project, viewer decision, tampering, expiry, revocation, direct asset access, and superseding an approved round. Cloudflare Access enrollment, issuer/audience configuration, raw-origin behavior, alternate hostnames, and public R2 bypass checks have not been run; staging remains unconfigured and must be separately authorized. See the README staging checklist.

## M5 release implementation — 2026-11-07

The release record binds one sealed sanitized render model to a frozen revision/hash, a single `astro-renderer-m1`, a content-addressed asset manifest, and an explicit allowed hostname. Payment and authority are manual operator evidence records; a UI selection does not replace provider verification for a real payment or domain. The active project/hostname D1 lock remains held for `unknown` and `needs_reconciliation`; retries are refused until a release operator reconciles provider state. Rollback requires a retained prior provider version. First-release takedown uses a deny/maintenance marker and is verified before the lock is released.

M5 adds a `workflow_dispatch` release-ID-only workflow protected by GitHub's `release-fixture` environment. Its provider is intentionally fake and `LIVE_DEPLOY_ENABLED=false`; live Cloudflare provisioning/deploy, raw-origin and alternate-host bypass checks, DNS/TLS validation, real payment reconciliation, and a real provider rollback were not authorized or performed. Before any staging release, require protected environment reviewers and a least-privilege release token, verify raw origin/alternate hostname and direct asset access, and rehearse reconciliation and rollback against a dedicated staging target. Portable exports include only the sanitized model, shared source, licensed content-addressed assets and notices; Places result data, review grants and private intake are excluded.
